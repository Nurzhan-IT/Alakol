# Анализ требований к серверу и возможности пользователей
## Проект: Alakol Hotel Management System (HMS)

---

## 1. Обзор проекта

### Архитектура системы
- **Фреймворк**: Django 4.2.2
- **База данных**: PostgreSQL 17.5
- **Кэширование**: Redis (django-redis)
- **Веб-сервер**: Gunicorn (предполагается)
- **ОС**: Ubuntu VPS
- **Дополнительные компоненты**: 
  - Celery для асинхронных задач
  - Скрипт управления кэшем (read/update операции)
  - Система логирования
  - Мультиязычная поддержка (русский, казахский, английский)

### Особенности проекта
- **Тип**: Система бронирования отелей (SaaS платформа)
- **Приложения**: 7 основных модулей (hotel, booking, userauths, legal, search, robokassa, addon)
- **Модели данных**: 15+ сложных моделей с множественными связями
- **Медиафайлы**: Галереи отелей, изображения номеров
- **Интеграции**: Robokassa (платежи), AWS SES (email), статические файлы
- **Кэширование**: Продвинутая система с Redis (2 кластера), TTL от 60 секунд до 24 часов

## 4. Предположения и методология

### Поведение пользователей
- **Средняя сессия**: 20-35 минут
- **Страниц за сессию**: 8-15
- **Время между запросами**: 15-30 секунд
- **Поиск отелей**: 60% пользователей
- **Просмотр деталей**: 40% от поисков
- **Завершение бронирования**: 5-8% от просмотров

### Нагрузка на компоненты

**Django приложение:**
- CPU: Средняя загрузка 30-50% при пиковой нагрузке
- RAM: 50-100 MB на worker процесс
- Workers: Рекомендуется (2 × CPU cores) + 1

**PostgreSQL:**
- Чтение/запись: 80/20 (типично для booking систем)
- Индексы: Критически важны для поиска отелей и проверки доступности
- Connections: Рекомендуется max_connections = 100-200

**Redis:**
- Hit rate: Ожидается 85-95%
- Память: ~100-200 MB на 1000 активных пользователей
- Expires: Настроено от 60 секунд до 24 часов

### Дополнительный скрипт
- **Операции**: Только чтение и обновление
- **Частота**: Каждые 5 минут (cron)
- **Влияние**: Минимальное (<5% CPU, <100 MB RAM)
- **I/O**: Преимущественно чтение из Redis и PostgreSQL

## 5. Потенциальные узкие места и оптимизации

### Критические узкие места

#### 1. База данных PostgreSQL
**Проблемы:**
- Сложные JOIN запросы для поиска номеров с фильтрацией
- Проверка доступности номеров (date range queries)
- Частые UPDATE операции при бронировании

**Оптимизации:**
```sql
-- Оптимизация индексов для поиска
CREATE INDEX CONCURRENTLY idx_room_availability 
ON booking_roomunavailability (room_id, start_date, end_date);

-- Партиционирование таблицы бронирований по дате
CREATE TABLE hotel_booking_y2024 PARTITION OF hotel_booking 
FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
```

**Настройки PostgreSQL:**
```ini
# postgresql.conf оптимизации
shared_buffers = 25%_of_RAM                    # 2GB для 8GB RAM
effective_cache_size = 75%_of_RAM               # 6GB для 8GB RAM
random_page_cost = 1.1                          # Для SSD
work_mem = 64MB                                 # Для сложных запросов
maintenance_work_mem = 512MB                    # Для индексирования
checkpoint_completion_target = 0.9
wal_buffers = 16MB
```

#### 2. Redis кэширование
**Текущая конфигурация:**
- 2 кластера Redis (default + long_term)
- Сжатие данных (zlib)
- Connection pooling (50 connections)

**Дополнительные оптимизации:**
```python
# Оптимизированные настройки Redis
CACHES = {
    "default": {
        "OPTIONS": {
            "CONNECTION_POOL_KWARGS": {
                "max_connections": 100,          # Увеличить пул
                "health_check_interval": 30,
                "socket_keepalive": True,
                "socket_keepalive_options": {},
            },
            "SERIALIZER": "django_redis.serializers.msgpack.MSGPackSerializer",  # Быстрее pickle
        }
    }
}
```

#### 3. Статические файлы и медиа
**Проблемы:**
- Большие изображения отелей (~2-5 MB каждая)
- 80+ изображений в media/hotel_gallery/
- Отсутствие CDN

**Оптимизации:**
- Настройка CDN (CloudFlare/AWS CloudFront)
- Сжатие изображений при загрузке
- Lazy loading для галерей
- WebP формат для современных браузеров

### Рекомендации по масштабированию

#### Вертикальное масштабирование (приоритет)
1. **Увеличение RAM**: Наиболее эффективно для Django + PostgreSQL
2. **SSD → NVMe**: Критично для I/O intensive операций
3. **CPU upgrade**: При высоких RPS (>500)

#### Горизонтальное масштабирование
1. **Database читающие реплики**: Для поисковых запросов
2. **Redis кластер**: При превышении 4 GB cache
3. **Load balancer**: Для распределения Django workers
4. **Microservices**: Выделение payment/booking в отдельные сервисы

## 6. Формулы расчета пользователей

### Базовые метрики производительности

#### Пропускная способность сервера
```
Max RPS = (CPU_cores × 100) × CPU_efficiency_factor
CPU_efficiency_factor = 0.3-0.7 (зависит от сложности запросов)

Для 4 ядер: Max RPS = 4 × 100 × 0.5 = 200 RPS
Для 8 ядер: Max RPS = 8 × 100 × 0.5 = 400 RPS
```

#### Память на пользователя
```
RAM_per_concurrent_user = Django_worker_memory + DB_cache + Redis_cache + Session_data
= 50MB + 20MB + 10MB + 5MB = 85MB

Concurrent_users = Available_RAM / RAM_per_user
Для 8 GB: ~70-80 одновременных пользователей
Для 16 GB: ~150-170 одновременных пользователей
```

#### Дневные пользователи
```
Daily_users = Concurrent_users × Session_turnover_rate × Active_hours
Session_turnover_rate = 1440_minutes / Average_session_duration
Active_hours = 12-16 часов (в зависимости от географии)

Пример для 8 GB сервера:
Daily_users = 75 × (1440/25) × (14/24) = ~2,500 пользователей
```

### Расчет нагрузки на базу данных
```
DB_connections_needed = Concurrent_users × 0.3  # 30% пользователей активно используют DB
DB_queries_per_second = Concurrent_users × Average_queries_per_user_per_second

Average_queries_per_user_per_session = 15-25 запросов
Average_session_duration = 25 минут
Queries_per_second_per_user = 25 / (25 × 60) = 0.017 QPS per user
```

## 7. Заключение и рекомендации

### Оптимальная стратегия развертывания

| Фаза | DAU | Конфигурация | Приоритеты | Стоимость |
|------|-----|-------------|------------|-----------|
| Стартовая | до 1,000 | 4 CPU, 8 GB RAM | Мониторинг, оптимизация запросов | $50-80/месяц |
| Рост | 1,000-5,000 | 8 CPU, 16 GB RAM | CDN, читающие реплики PostgreSQL | $150-250/месяц |
| Масштаб | 5,000+ | 16 CPU, 32 GB RAM | Микросервисы, автомасштабирование | $400-600/месяц |

### Ключевые метрики для мониторинга
1. **Время отклика**: <300ms для 95% запросов
2. **CPU загрузка**: <70% в пиковые часы
3. **RAM использование**: <80% от доступной
4. **PostgreSQL connections**: <70% от max_connections
5. **Redis hit rate**: >90%
6. **Disk I/O**: <80% utilization

### Критические точки внимания
- **Бронирование в реальном времени**: Требует минимизации кэширования критических данных
- **Платежные операции**: Требуют высокой надежности и быстродействия
- **Сезонность**: Система бронирования отелей имеет пиковые периоды (лето, праздники)
- **Локализация**: Поддержка 3 языков увеличивает требования к памяти на ~30%
